# Technical Report — Simple OCR with LangChain

Author: Fatma Ezzahra Elfilali

## 1. Problem and objectives

Scanned invoices, receipts and forms hold data that cannot be searched or
queried. OCR alone produces a wall of text; the business value appears when the
text is interpreted: which document is it, what is the total, what is due and
when, is anything illegible.

Objectives:

1. reliable text extraction with per-line confidence;
2. an engine abstraction so backends can be swapped;
3. structured interpretation validated by a schema;
4. grounded question answering over the extracted text;
5. measurable OCR quality (CER/WER/field recall), not just "it looks right";
6. CLI and web interfaces over the same pipeline.

## 2. Components

| Component | File | Responsibility |
| --- | --- | --- |
| `OcrEngine` (ABC) | `engines.py` | backend contract |
| `RapidOcrEngine` | `engines.py` | PP-OCR via onnxruntime, lazy model loading |
| `TesseractEngine` | `engines.py` | pytesseract with word-to-line merging |
| `preprocess()` | `engines.py` | grayscale, upscale, autocontrast |
| `DocumentPipeline` | `pipeline.py` | extract → understand → ask → clean |
| `StructuredDocument` | `schema.py` | Pydantic contract + field coercion |
| `extract_json()` | `parsing.py` | fences, prefaces, trailing commas |

### 2.1 Engine abstraction

`OcrEngine` has one required method, `extract(image, language) -> OcrResult`.
Two implementations are provided. RapidOCR is the default because it installs
with pip and needs no system binary — a real constraint on student machines.
Tesseract is kept because it is common and has language packs for Arabic.

Lazy loading matters: importing RapidOCR takes seconds and loads ONNX models.
`RapidOcrEngine` defers that until the first `extract()` call, which keeps the
tests and `--help` fast.

### 2.2 Normalising two very different backends

RapidOCR returns line-level boxes; Tesseract returns word-level boxes. The
pipeline needs comparable output, so `group_words_into_lines()` clusters words
by vertical proximity and horizontal order, producing line objects with merged
bounding boxes and averaged confidence. Without this, the LLM would receive one
word per line from Tesseract and lose sentence context.

### 2.3 Confidence as a first-class signal

`OcrResult.mean_confidence` and `low_confidence_words` are surfaced in the UI,
in the CLI and injected into the LLM's warnings. The prompt is instructed to
leave a field empty and add a warning rather than guess. This is the main
mitigation against hallucinated amounts.

### 2.4 Two prompts, two jobs

- `understanding_prompt` asks for a fixed JSON schema (type, summary, fields,
  tables, warnings) so the output can be validated.
- `qa_prompt` answers one question from the OCR text only, and is instructed to
  say when the document does not contain the answer. Separating them avoids the
  common failure where a "summarise" prompt is reused for a factual question
  and the model paraphrases instead of answering.

## 3. Environment

Python 3.12, LangChain 0.3.x, onnxruntime via `rapidocr-onnxruntime`,
Pillow, Streamlit, Pydantic. Model: `mistral` 7B Q4_K_M through Ollama.
Sample documents are generated by `scripts/make_samples.py`, so the ground truth
is known exactly and no binary files need to be committed.

## 4. Testing and results

### 4.1 Unit tests (24 tests)

- engine dispatch and unknown-engine rejection;
- Tesseract absence produces a clear error instead of a stack trace;
- a rendered image really is read (`170.28` appears in the output) — this is an
  integration test of the OCR path;
- preprocess changes mode and size;
- word-to-line grouping, including empty input;
- pipeline: structured document built, fenced JSON accepted, invalid JSON
  reported, empty OCR skips the model, low confidence adds a warning, model
  exception is reported not raised, flat-dict fields coerced, string warnings
  coerced, prompt contains the wrapped OCR text and the answer language;
- Q&A rejects an empty question and uses the document text;
- evaluation helpers: Levenshtein, CER/WER edge cases, whitespace-normalised
  field recall.

Tests use a fake engine and a scripted model, so no model server or GPU is
needed.

### 4.2 OCR quality

`scripts/evaluate_ocr.py` compares extraction against exact ground truth:

| Metric | Meaning |
| --- | --- |
| CER | character error rate (Levenshtein / reference length) |
| WER | word-level error rate |
| field recall | share of expected values found verbatim |
| latency | milliseconds per image |

Measured on the two generated documents (see `docs/ocr_evaluation.json`):

| Document | Variant | Raw CER | Flattened CER | WER | Field recall |
| --- | --- | --- | --- | --- | --- |
| invoice | raw | 0.446 | 0.047 | 0.047 | 3/4 |
| invoice | 2× upscale | 0.417 | **0.018** | 0.018 | 3/4 |
| receipt | raw | 0.305 | 0.031 | 0.031 | 2/2 |
| receipt | 2× upscale | 0.282 | **0.000** | 0.000 | 2/2 |

Two conclusions that are worth defending:

1. **Raw CER is misleading here.** PP-OCR returns one box per visual line, so a
   four-column table row arrives as four lines while the ground truth has one.
   Most of the 0.28–0.45 raw error is line segmentation, which is why the
   flattened CER (whitespace collapsed) is reported next to it. Attribution
   matters: a metric that penalises layout is not a recognition failure.
2. **Upscaling is a real improvement, not a placebo.** At the native size
   PP-OCR drops intra-line spaces ("Duedate:2026-11-12", "ACMESUPPLIESSARL")
   because wide crops are squeezed into the recogniser's 320-px input. At 2×
   the spacing is preserved and flattened CER falls from 0.039 to 0.009 on
   average. The one remaining invoice miss is the supplier header
   (`ACMESUPPLIESSARL`, all-caps with no spaces), which no amount of resizing
   fixed — it is repaired correctly by the LLM cleanup chain.

## 5. How LangChain contributes

OCR produces text; LangChain turns text into a contract. The prompt template
holds the schema and the "verbatim values" rule, the model abstraction allows
local or cloud execution, the parser plus tolerant JSON extraction absorbs
imperfect generations, and Pydantic enforces the contract before anything
reaches the UI. Splitting understanding, Q&A and cleanup into three chains
keeps each prompt focused, which measurably improves small-model behaviour.

## 6. Limitations

1. Handwriting, rotated pages and photos with perspective distortion fail.
2. RapidOCR's default models are Latin-oriented; Arabic/Chinese need a
   different model set.
3. Table structure is lost: columns become plain text.
4. Only the first PDF page is rendered.
5. The LLM can still invent a value for an illegible cell; confidence warnings
   reduce but do not remove that risk.
6. CPU-only inference is slow for large images (roughly 0.5–2 s each).

## 7. Improvements

1. Add deskewing, adaptive thresholding and rotation detection with OpenCV.
2. Use a layout/table model (`unstructured`, LayoutLM) for table reconstruction.
3. Render all PDF pages and merge with page numbers as fields.
4. Cache by image hash to avoid repeated OCR.
5. Add a review UI where low-confidence fields are edited by a human and the
   correction is logged (a cheap active-learning loop).
6. Evaluate on real scanned invoices, not only generated ones.
